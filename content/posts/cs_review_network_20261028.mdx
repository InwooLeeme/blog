오늘은 『면접을 위한 CS 전공지식 노트』를 읽고 두 가지 공부를 했다. 먼저 어제 배운 싱글톤·팩토리·전략·옵저버·프록시 패턴을 복습했고, 새로 네트워크 기초부터 **2.3.3 인터넷 계층을 처리하는 기기**까지 읽었다.

읽은 내용을 내 말로 설명할 수 있는지 확인하려고 퀴즈를 풀었다. 패턴 이름은 기억해도 적용 이유를 정확히 설명하지 못하거나, 네트워크 용어의 의미를 반대로 기억한 부분이 있었다.

이번 글은 학습 범위 전체를 옮긴 요약이 아니라, **퀴즈에서 설명한 내용과 피드백을 통해 바로잡은 부분을 묶은 기록**이다. 디자인 패턴의 첫 학습 내용은 [어제 작성한 글](/blog/design_patterns_20261027)에 정리했다.

## 1. 디자인 패턴 복습: 이름보다 역할을 구분하기

### 싱글톤은 하나의 객체를 보장할 뿐이다

싱글톤 장바구니 하나에 모든 사용자가 상품을 추가하면, 사용자들의 상품 목록이 섞일 수 있다. 이를 보고 처음에는 “내부 구성물은 공유하면 안 된다”고 답했다.

하지만 모든 내부 데이터를 공유하면 안 되는 것은 아니다. **변하지 않는 공통 설정은 공유할 수 있지만, 사용자마다 달라지는 상태는 분리해야 한다.** 싱글톤 서비스 안에서 사용자 ID별로 장바구니를 관리하는 설계도 가능하다.

공통 설정을 사용하는 기능 하나가 설정값을 바꿔 다른 기능까지 영향을 받는 상황에서는, 필요한 값을 파라미터로 넘기는 방법을 생각했다. 이때도 같은 변경 가능한 객체를 그대로 넘기면 문제가 남는다. 공통 설정은 읽기 전용으로 두고, 기능별 값이나 독립적인 복사본을 전달해야 한다.

또한 싱글톤이라고 해서 스레드 안전성이 자동으로 확보되지는 않는다.

```text
공유 값: 0
스레드 A: 0을 읽음
스레드 B: 0을 읽음
스레드 A: 1을 저장
스레드 B: 1을 저장
결과: 두 번 증가시켰지만 값은 1
```

객체를 하나로 유지하는 것과 그 객체의 상태에 안전하게 접근하는 것은 별개의 문제다. 공유 상태를 수정해야 한다면 락이나 원자적 연산 등 적절한 동시성 제어가 필요하다.

### 팩토리와 전략: 생성과 수행 방식의 차이

“결제 수단에 따라 카드 또는 계좌이체 객체를 생성한다”는 질문에서 처음에는 전략 패턴이라고 생각했다. 상황에 따라 종류가 달라진다는 점에만 집중한 것이다.

둘을 구분하는 기준은 **무엇을 분리하는가**다.

| 패턴 | 핵심 역할 | 결제 예시 |
|---|---|---|
| 팩토리 | 객체 생성 방식을 분리 | 카드·계좌이체 결제 객체 생성 |
| 전략 | 수행할 알고리즘이나 방식을 교체 | 선택한 결제 방식으로 결제 실행 |

두 패턴을 함께 사용할 수도 있다. 아래는 설명을 위한 의사 코드다.

```text
payment = factory.create("계좌이체")
paymentService.setStrategy(payment)
paymentService.pay()
```

기존 카드 객체 자체를 계좌이체 객체로 바꾸는 것이 아니다. 팩토리가 계좌이체 객체를 생성하고, 결제 서비스가 사용할 전략을 교체한다.

알림 기능도 마찬가지다. 푸시 알림을 추가할 때 공통 `send()` 인터페이스를 구현하는 클래스를 만들고 팩토리를 확장하면, 사용하는 쪽의 `send()` 호출은 그대로 유지할 수 있다. 단, 공통 인터페이스와 사용 조건이 유지된다는 전제가 필요하다.

### 전략 패턴을 선택하는 기준은 분기 개수만이 아니다

일반 회원 0%, VIP 10%, 임직원 20% 할인을 적용하는 문제에서는 경우의 수가 적으니 `if`문을 쓰면 된다고 답했다. 단순한 문제에 패턴을 억지로 적용할 필요가 없다는 방향은 맞았다.

다만 핵심 기준은 경우의 수보다 **계산 방식이 얼마나 달라지는가**다.

```text
할인율 = { 일반: 0, VIP: 0.1, 임직원: 0.2 }
최종 가격 = 가격 × (1 − 할인율[등급])
```

공식이 같다면 할인율만 데이터로 관리해도 된다. 반대로 종류가 세 개뿐이어도 정액 할인·묶음 할인·최대 할인 한도처럼 로직이 다르면 전략 분리가 도움이 될 수 있다.

### 옵저버는 이벤트가 아니라 이벤트에 반응하는 객체다

주문 완료 상황에서 관찰 대상은 주문, 옵저버는 주문 완료라고 답했다. 이 부분은 잘못 구분했다.

| 구분 | 주문 예시 | 유튜브 예시 |
|---|---|---|
| 관찰 대상 | 주문 상태를 관리하고 알리는 객체 | 채널 |
| 이벤트 | 주문 완료 | 새 영상 업로드 |
| 옵저버 | 이메일 발송·재고 갱신·포인트 적립 담당 객체 | 구독자 |

배송 준비 알림을 추가한다면 새로운 옵저버를 만들어 등록한다. 기존 옵저버를 바꾸는 것이 아니라 **같은 이벤트를 받아 처리할 대상을 추가하는 것**이다.

구독을 취소할 때는 관찰 대상의 목록에서 해당 옵저버를 제거해야 한다. 사용자 객체 자체를 삭제하는 것은 아니다.

중복 알림을 막으려면 중복 등록도 방지해야 한다. 메모리에서는 구독자 ID를 키로 하는 `Set`이나 `Map`을 사용할 수 있다. DB에서는 `(채널 ID, 구독자 ID)` 조합에 유일성 제약을 두는 방법이 있다. 등록 전 조회만 하면 동시 요청이 둘 다 “등록되지 않음”을 확인할 수 있으므로 저장 단계의 제약도 중요하다.

한 옵저버에서 오류가 발생해도 나머지가 알림을 받게 하려면 **실패를 서로 분리**해야 한다. 병렬 처리를 떠올렸지만, 병렬 실행 자체가 이를 보장하지는 않는다. 순차 처리에서도 구독자별로 예외를 처리하고 다음 대상으로 계속 진행할 수 있다.

### 프록시는 권한 검사만 하는 것이 아니다

이미지 지연 로딩을 프록시로 구현하는 문제는 처음에 잘 설명하지 못했다. 프록시를 권한 검증과 연결해서만 생각한 부분도 있었다.

프록시는 실제 객체 앞에서 요청을 받아 필요한 처리를 한 뒤 실제 객체에 위임한다. 목적에 따라 역할이 달라진다.

- **가상 프록시:** 실제 객체가 필요해질 때까지 생성이나 로딩을 미룬다.
- **보호 프록시:** 권한을 확인해 실제 객체에 대한 접근을 제어한다.

이미지 프록시는 표시 요청이 들어오면 실제 이미지가 있는지 확인한다. 없으면 로딩하고, 이미 로딩해 보관 중이라면 재사용한다. 프록시와 실제 이미지가 같은 `display()` 인터페이스를 제공하면 사용하는 코드는 둘을 구분하지 않아도 된다.

권한 검사와 지연 로딩을 함께 적용할 수도 있다. 다만 지연 로딩이 이미 로딩한 데이터를 자동으로 정리해 주는 것은 아니다.

## 2. 네트워크 기초: 많은 데이터를 보내는 것과 빨리 반응하는 것

### 처리량과 지연 시간은 직접 비교할 수 없다

큰 파일은 빠르게 내려받지만 온라인 게임 반응은 늦은 상황을 설명하면서, 처음에는 처리량과 지연 시간을 서로 크고 빠른 값처럼 비교했다.

두 지표는 측정하는 대상과 단위가 다르다.

| 지표 | 의미 | 단위 예시 |
|---|---|---|
| 처리량 | 일정 시간에 실제로 전달한 데이터의 양 | Mbps |
| 지연 시간 | 데이터가 전달되는 데 걸리는 시간 | ms |

**처리량이 높으면서 지연 시간도 긴 네트워크가 있을 수 있다.**

큰 파일 다운로드에서는 많은 데이터를 받아야 하므로 처리량이 중요하다. 게임에서는 작은 입력과 응답을 빠르게 주고받아야 하므로 지연 시간이 크게 체감된다. 큰 파일도 지연 시간의 영향을 받지만, 두 상황에서 특히 중요한 요소가 다르다.

`ping`에서는 주로 왕복 시간인 **RTT**와 응답 손실 비율을 확인할 수 있다. 응답 시간이 짧다고 대용량 다운로드도 반드시 빠르다고 판단할 수는 없다. 또한 응답이 없다는 사실만으로 서버가 꺼졌다고 단정할 수는 없다. 중간 장비나 서버가 해당 요청을 차단할 수도 있기 때문이다.

### 병목은 전체 경로에서 찾아야 한다

```text
내 컴퓨터 → 구간 A: 1Gbps → 구간 B: 100Mbps → 서버
```

다른 제한이 없다면 구간 B가 전체 전송을 제한한다. 구간 A만 10Gbps로 높여도 데이터는 B를 통과해야 하므로 전체 처리량이 크게 증가하지 않는다.

처리할 수 있는 양보다 데이터가 빠르게 들어오면 대기열이 길어지거나 패킷이 버려질 수 있다. 따라서 성능 개선은 **어느 구간이 제한을 만드는지 확인하는 것**부터 시작해야 한다.

### 연결 구조는 장애 범위에도 영향을 준다

스타형 토폴로지에서는 각 컴퓨터가 중앙 장비에 연결된다. 연결선 하나가 고장 나면 해당 컴퓨터의 통신이 영향을 받지만, 중앙 장비가 고장 나면 연결된 전체 통신이 중단될 수 있다.

이런 중앙 장비는 단일 장애점(SPOF)이 될 수 있다. 컴퓨터 자체가 모두 고장 나는 것이 아니라, 중앙 장비를 이용하는 통신이 안 되는 것이다.

지역 범위에 따른 분류도 복습했다. 사무실·건물처럼 제한된 지역은 LAN, 도시 규모는 MAN, 멀리 떨어진 지역의 네트워크를 연결하는 광역망은 WAN으로 구분한다.

## 3. 프로토콜과 계층: 무엇을 약속하고 무엇을 분리하는가

프로토콜의 예로 HTTP를 답했지만, 프로토콜 자체의 의미도 설명할 수 있어야 한다.

**프로토콜은 메시지 형식과 의미, 주고받는 절차 등을 정한 공통 규칙이다.** 연결되어 데이터를 전달할 수 있어도 상대방이 그 데이터를 해석하지 못하면 의도한 통신을 할 수 없다.

TCP/IP 4계층은 통신에 필요한 역할을 나눈다.

| 계층 | 주요 역할 | 관련 정보·예시 |
|---|---|---|
| 애플리케이션 | 애플리케이션 간 메시지 교환 | HTTP, URL 경로 |
| 전송 | 애플리케이션 간 데이터 전달 | TCP, UDP, 포트 번호 |
| 인터넷 | 네트워크를 거치는 패킷 전달 | IP 주소 |
| 링크 | 연결된 구간에서 데이터 전달 | 이더넷, Wi-Fi |

계층 사이의 약속이 유지되면 한 계층의 구현이 바뀌어도 다른 계층이 받는 영향을 줄일 수 있다. 유선 연결에서 Wi-Fi로 바꿔도 브라우저가 HTTP를 사용하는 방식은 유지되는 것이 한 예다. 다만 전환 순간 기존 연결이 끊기거나 재연결이 필요할 수는 있다.

역할을 나눠 변경 영향을 줄인다는 점에서 MSA가 떠올랐다. 공통점은 있지만 같은 개념은 아니다. TCP/IP는 통신 기능을 계층으로 나누고, MSA는 보통 업무 기능을 독립적인 서비스로 나눈다.

## 4. TCP와 UDP: 신뢰성과 기다림의 차이

TCP와 UDP를 설명할 때 “TCP는 빠르고, UDP는 느리지만 정확하다”고 답했다. 핵심 특성을 반대로 기억하고 있었다.

**TCP는 신뢰성 있고 순서가 보장되는 바이트 스트림을 제공한다.** 손실된 데이터를 재전송하고 순서를 맞추지만, 이 과정에서 기다리는 시간이 늘어날 수 있다. 연결이 실패하는 상황까지 무조건 전달을 보장한다는 뜻은 아니다.

**UDP 자체는 전달 여부나 순서를 보장하지 않는다.** TCP와 같은 연결 설정이나 재전송 절차가 없어 지연에 민감한 통신에 활용할 수 있다. 그렇다고 항상 TCP보다 빠르다고 단정할 수는 없다. 필요한 신뢰성 처리를 애플리케이션에서 추가하기도 한다.

파일 다운로드는 빠진 부분 없이 온전한 데이터를 받는 것이 중요하다. 실시간 음성 통화는 오래된 소리를 뒤늦게 받기보다 일부 손실이 있더라도 현재 대화를 이어가는 것이 중요할 수 있다.

### 연결 설정과 종료를 구분하기

TCP의 연결 설정을 묻자 `TIME_WAIT`이 먼저 떠올랐다. 연결 설정과 종료 과정을 섞어서 기억한 것이다.

연결 설정은 다음과 같은 **3-way handshake**를 사용한다.

```text
클라이언트 → 서버: SYN
서버 → 클라이언트: SYN + ACK
클라이언트 → 서버: ACK
```

SYN은 연결 설정을 위한 순서 번호 동기화에, ACK는 상대방이 보낸 내용의 수신 확인에 사용된다.

`TIME_WAIT`은 연결 종료 과정의 상태다. 늦게 도착하는 이전 연결의 패킷에 대비하고, 상대가 마지막 ACK를 받지 못해 FIN을 다시 보내면 응답할 수 있도록 기다린다. 일반적인 종료 흐름에서는 먼저 종료를 요청한 쪽에서 나타난다.

## 5. 캡슐화와 PDU: 데이터에 정보를 붙이는 이유

송신 측에서는 데이터가 계층을 내려가면서 헤더 등의 정보를 붙인다. 각 계층이 전달과 처리를 수행하는 데 필요한 정보다.

예를 들어 전송 계층에는 포트 번호, 인터넷 계층에는 IP 주소가 포함된다. 이더넷에서는 MAC 주소와 오류 검출 정보 등을 사용한다.

수신 측은 각 계층에서 해당 정보를 해석하고 처리한 뒤 상위 계층으로 넘긴다. 보내는 쪽의 과정을 **캡슐화**, 받는 쪽의 과정을 **역캡슐화**라고 한다.

계층에서 다루는 데이터 단위인 PDU는 다음처럼 구분했다.

| 대상 | 데이터 단위 |
|---|---|
| TCP | 세그먼트 |
| UDP | 데이터그램 |
| 인터넷 계층 | 패킷 또는 IP 데이터그램 |
| 이더넷 같은 링크 계층 | 프레임 |

## 6. 라우터와 L7 스위치: 읽는 정보가 다르다

다음과 같이 요청을 나누고 싶다고 가정해 보자.

```text
/images → 이미지 서버
/api    → API 서버
```

처음에는 이미지가 크고 API 응답이 작을 수 있어서 L7 스위치가 적합하다고 설명했다. 하지만 이 예제의 분산 기준은 크기가 아니라 **URL 경로**다.

라우터는 목적지 IP 주소와 라우팅 테이블을 바탕으로 다음 전달 경로를 결정한다. 기본적인 패킷 전달을 위해 HTTP의 URL이나 본문까지 해석할 필요는 없다. L3 스위치도 인터넷 계층에서 IP 기반 전달을 수행한다.

반면 L7 스위치는 HTTP 같은 애플리케이션 계층의 정보를 활용할 수 있다. 두 요청의 IP와 포트가 같더라도 URL 경로를 확인하면 다른 서버로 보낼 수 있다.

이때 URL 경로가 전송 계층의 정보라고 답한 것도 바로잡았다.

- 인터넷 계층: **IP 주소**
- 전송 계층: **포트 번호**
- 애플리케이션 계층: **HTTP의 URL 경로와 헤더**

HTTPS에서는 경로도 암호화되므로, 이를 기준으로 처리하려면 TLS 종료 등을 통해 복호화된 요청에 접근할 수 있어야 한다.

라우터가 선택하는 최적 경로도 단순히 거치는 라우터 수가 가장 적은 경로를 뜻하지 않는다. 대역폭이나 지연 같은 요소가 기준이 될 수 있지만, 실제 선택 방식은 라우팅 프로토콜과 설정에 따라 달라진다. 모든 라우터가 실시간 지연과 대역폭을 직접 측정해 판단하는 것은 아니다.

## 7. 오늘 답변에서 바로잡은 내용

| 처음 생각한 내용 | 복습 후 정리 |
|---|---|
| 종류에 따라 객체를 만들면 전략 패턴이다 | 생성은 팩토리, 수행 방식 교체는 전략의 관심사다 |
| 주문 완료가 옵저버다 | 주문 완료는 이벤트이고, 반응하는 담당 객체가 옵저버다 |
| 프록시는 검증을 하는 객체다 | 권한 제어뿐 아니라 지연 로딩 등에도 쓰인다 |
| 분기가 많아지면 전략 패턴을 쓴다 | 분기 수보다 계산 방식의 차이와 변경 요구가 중요하다 |
| 처리량과 지연 시간을 크기로 비교할 수 있다 | 서로 다른 대상과 단위를 측정하는 지표다 |
| UDP는 느리지만 정확하다 | UDP 자체는 전달과 순서를 보장하지 않는다 |
| TIME_WAIT은 연결 설정 과정이다 | 연결 종료 과정의 상태다 |
| URL 경로는 전송 계층에서 확인한다 | HTTP의 URL 경로는 애플리케이션 계층 정보다 |

디자인 패턴과 네트워크는 다른 주제지만, 설명이 막힐 때 확인할 질문은 비슷했다. **누가 어떤 역할을 맡고, 어떤 정보를 바탕으로 동작하는가?**

다음 복습에서는 이름을 맞히는 데서 끝내지 않고, 적용 이유와 적용하지 않아도 되는 경우까지 설명해 보려고 한다.
