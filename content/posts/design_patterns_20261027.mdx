오늘은 『면접을 위한 CS 전공지식 노트』를 읽으며 싱글톤, 팩토리, 전략, 옵저버, 프록시 패턴을 공부했다.

처음에는 각 패턴의 장점을 대부분 “유지보수가 쉬워진다”로 설명했다. 하지만 퀴즈를 풀어 보니, **무엇을 분리하고 어떤 변경에 대응하기 쉬워지는지**까지 설명해야 패턴의 목적을 제대로 이해할 수 있다는 것을 알게 됐다.

이번 글은 책을 읽고 퀴즈에 답하며 정리한 학습 기록이다. 책의 문장을 옮기기보다는 내가 이해한 내용과 답변에서 보완한 부분을 중심으로 적었다.

## 1. 싱글톤 패턴

싱글톤 패턴은 클래스의 인스턴스를 하나만 유지하고, 이를 여러 곳에서 사용할 수 있도록 하는 패턴이다.

프로그램 전체에서 동일한 설정 관리 객체를 사용하는 상황을 예로 들 수 있다. 객체를 사용하는 곳마다 따로 생성하지 않고, 하나의 인스턴스를 공유한다.

### 장점과 주의할 점

객체의 중복 생성을 막고, 여러 곳에서 동일한 상태를 사용할 수 있다. 다만 객체를 하나만 만든다고 해서 유지보수가 자동으로 쉬워지는 것은 아니다.

여러 코드가 공유 객체의 상태를 변경할 수 있다면, 한 곳의 변경이 다른 곳의 동작에도 영향을 줄 수 있다. 테스트 사이에 상태가 남아 서로 영향을 주거나, 여러 스레드가 동시에 접근하면서 문제가 생길 수도 있다.

처음에는 이 단점을 “하나만 깨져도 다 깨진다”라고 답했다. 더 정확히 표현하면 다음과 같다.

> 공유 객체의 상태가 잘못 변경되면, 그 객체에 의존하는 여러 곳에 문제가 전파될 수 있다.

또한 인스턴스를 안전하게 하나만 생성하는 것과, 생성된 객체의 상태를 여러 스레드에서 안전하게 사용하는 것은 별개의 문제다.

## 2. 팩토리 패턴

팩토리 패턴의 핵심은 **객체를 생성하는 코드와 사용하는 코드를 분리하는 것**이다.

이메일, 문자, 푸시 알림을 보내는 프로그램을 생각해 보자. 알림을 사용하는 코드가 각 객체의 생성 방법을 모두 알고 있다면, 생성 방식이 바뀔 때마다 사용하는 코드도 수정해야 할 수 있다.

팩토리에 생성을 맡기면 사용하는 쪽은 구체적인 생성 과정을 몰라도 된다. 필요한 객체를 전달받아 공통 인터페이스로 사용하면 된다.

### 무엇이 바뀌기 쉬워지는가?

생성자에 필요한 정보나 구체적인 구현이 변경되더라도, 사용하는 인터페이스가 유지된다면 변경을 생성 담당 코드에 모을 수 있다.

퀴즈에서는 “객체를 어떻게 생성하는지는 몰라도 되고, 생성하는 곳이 바뀌더라도 코드를 수정하지 않아도 된다”라고 답했다. 여기서 “생성하는 곳”을 **“구체적인 객체 종류나 생성 방식”**으로 바꾸면 의도가 더 분명해진다.

다만 팩토리를 쓴다고 모든 수정이 사라지는 것은 아니다. 새로운 종류를 지원하기 위해 팩토리를 수정해야 할 수 있고, 공통 인터페이스 자체가 바뀌면 사용하는 코드에도 영향이 있다.

여기서는 팩토리 메서드와 추상 팩토리의 세부 차이보다는, 객체 생성 책임을 분리한다는 공통 목적에 집중했다.

## 3. 전략 패턴

전략 패턴은 **같은 목적을 수행하는 여러 알고리즘을 각각 분리하고, 공통 인터페이스를 통해 교체할 수 있도록 하는 패턴**이다.

쇼핑몰의 할인 계산을 예로 들 수 있다.

- 일반 회원 할인
- VIP 회원 할인
- 이벤트 할인

이 모든 계산을 하나의 함수에서 조건문으로 처리하면 할인 종류가 늘어날수록 함수가 복잡해진다. 한 할인 로직을 수정할 때 다른 할인 로직까지 함께 살펴봐야 할 수도 있다.

각 할인 방식을 전략으로 분리하면 할인 알고리즘을 독립적으로 수정하고 테스트할 수 있다. 할인을 적용하는 쪽은 선택된 전략에 계산을 맡긴다.

### 조건문이 모두 없어지는 것은 아니다

전략 패턴을 적용해도 “어떤 전략을 선택할 것인가?”를 결정하는 조건문은 남을 수 있다.

핵심은 조건문을 없애는 데 있지 않다. **알고리즘의 구현을 분리하고, 이를 사용하는 코드가 특정 알고리즘에 덜 의존하도록 만드는 것**이 중요하다.

처음에는 전략 패턴을 “상황에 맞는 객체를 전략적으로 배치하는 것”이라고 설명했는데, 알고리즘을 분리하고 교체한다는 표현이 더 정확하다.

## 4. 옵저버 패턴

옵저버 패턴은 관찰 대상의 상태가 변경됐을 때, 등록된 관찰자에게 이를 알리는 패턴이다.

유튜브 채널과 구독자의 관계에 비유하면 이해하기 쉽다.

| 역할 | 예시 |
| --- | --- |
| 관찰 대상 | 유튜브 채널 |
| 옵저버 | 알림을 받을 구독자 |
| 변경 이벤트 | 새로운 영상 업로드 |
| 알림 | 등록된 구독자에게 새 영상 소식 전달 |

이는 패턴을 이해하기 위한 비유이며, 실제 유튜브의 내부 구현을 설명하는 것은 아니다.

### 구독 취소는 무엇을 의미할까?

구독 취소는 관찰 대상의 알림 목록에서 해당 옵저버를 제거하는 것이다. 구독자 객체 자체를 삭제하는 것은 아니다.

퀴즈에서는 “관찰 대상과 옵저버를 잇는 연결 관계를 끊는다”라고 답했다. 이를 코드의 관점에서 표현하면 **알림 대상 등록을 해제한다**고 설명할 수 있다.

관찰 대상은 개별 구독자의 구체적인 동작을 모두 알 필요 없이, 약속된 알림 인터페이스를 통해 변경을 전달할 수 있다.

다만 더 이상 알림을 받지 않아야 하는 옵저버의 등록을 해제하지 않으면 불필요한 처리가 이어질 수 있다. 구현에 따라 객체 참조가 계속 유지되는 문제도 생길 수 있으므로, 등록뿐 아니라 해제 시점도 고려해야 한다.

## 5. 프록시 패턴

프록시 패턴은 **원본 객체와 같은 인터페이스를 제공하는 대리 객체를 두고, 원본에 대한 접근을 제어하는 패턴**이다.

용량이 큰 이미지를 실제로 필요해질 때 로딩하는 상황을 예로 들 수 있다. 이미지 프록시를 먼저 만들어 두고, 이미지를 표시하는 시점에 원본을 로딩한다.

이처럼 원본 생성을 미루는 방식을 지연 로딩이라고 하며, 프록시 패턴의 활용 사례 중 하나다.

### 같은 인터페이스를 사용하는 이유

호출하는 코드는 상대가 프록시인지 원본인지 구분할 필요 없이 `display()` 같은 메서드를 호출할 수 있다.

프록시는 호출을 받으면 원본이 준비됐는지 확인하고, 필요하다면 로딩한 뒤 작업을 전달한다. 사용하는 코드는 이런 과정을 직접 처리하지 않아도 된다.

처음에는 같은 인터페이스의 장점을 단순히 “유지보수에 좋다”라고 답하고, 틀린 답이 아닐까 생각했다. 방향은 맞았지만 이유를 더 구체적으로 설명할 필요가 있었다.

> 원본 대신 프록시를 사용하더라도, 호출하는 코드를 바꾸지 않고 접근 제어 동작을 추가할 수 있다.

필요한 이미지만 로딩하면 초기 로딩 비용과 메모리 사용량을 줄일 수 있다. 다만 모든 이미지를 결국 로딩하고 계속 보관한다면, 최종 메모리 사용량까지 줄어드는 것은 아니다.

## 팩토리 패턴과 전략 패턴의 차이

두 패턴 모두 여러 종류의 객체를 다룰 수 있지만, 관심사는 다르다.

| 구분 | 팩토리 패턴 | 전략 패턴 |
| --- | --- | --- |
| 핵심 관심사 | 객체 생성 | 알고리즘과 동작의 교체 |
| 분리하는 것 | 생성 과정과 사용 코드 | 개별 알고리즘과 사용 코드 |
| 할인 기능의 예 | 할인 전략 객체를 생성 | 선택한 할인 전략으로 금액을 계산 |

팩토리가 할인 전략 객체를 만들고, 사용하는 코드가 그 전략에 계산을 맡기도록 구성할 수도 있다. 두 패턴은 서로 대체하는 관계가 아니라 함께 사용할 수 있는 도구다.
