Jenkins를 실습하면서 처음에는 화면에 `Hello`가 출력되는 것부터 시작했다. 그다음 GitHub에서 코드를 가져오고, Docker 이미지를 빌드하고, 테스트를 통과하면 앱을 실행하도록 단계를 붙였다.

명령을 하나씩 실행할 때는 각각 별개의 작업처럼 느껴졌는데, 연결하고 보니 흐름이 보였다. **코드 변경을 감지하고, 검사하고, 승인받아 배포한 뒤 정상 동작까지 확인하는 과정**이었다.

이번 글은 [docker_practice 저장소](https://github.com/InwooLeeme/docker_practice)의 설정과 실습 과정을 정리한 기록이다. 외부 서버에 배포한 구성은 아니고, Mac 안의 Docker 환경을 배포 대상으로 사용했다. 롤백 명령과 별도 작업은 뒤쪽에 실습 예제로 구분했다.

## 먼저 전체 흐름부터

```text
GitHub main에 코드 반영
        ↓
Jenkins가 주기적으로 변경 확인
        ↓
Docker 이미지 빌드
        ↓
백엔드 자동 테스트와 결과 수집
        ↓ 통과하면
사람의 배포 승인
        ↓
컨테이너 실행·교체
        ↓
healthcheck와 백엔드 응답 확인
        ↓
성공한 빌드의 커밋·이미지 태그 기록
```

여기서 빌드와 테스트가 CI에 해당하고, 통과한 앱을 실행 환경에 반영하는 부분이 배포에 해당한다. 현재는 승인 버튼을 둔 상태라서, 코드가 바뀌었다고 배포까지 무조건 자동으로 진행되지는 않는다.

## Mac 안에서 Jenkins와 앱은 어디서 실행될까?

실습에서는 Jenkins 컨테이너와 별도의 Docker 엔진 컨테이너를 사용했다. Jenkins에 설치한 Docker CLI가 TLS로 Docker-in-Docker 엔진에 접속하고, 실제 앱 컨테이너는 그 엔진이 실행한다.

```text
Mac / Docker Desktop
├─ Jenkins 컨테이너
│  └─ Docker CLI와 Compose
└─ Docker-in-Docker 엔진
   ├─ Next.js 프론트엔드
   └─ FastAPI 백엔드
```

처음 헷갈린 부분은 **Docker 명령이 있다는 것과 Docker 엔진이 있다는 것은 다르다**는 점이었다. Jenkins에서 `docker`를 실행하려면 CLI뿐 아니라 접속할 엔진도 필요했다. 이 구조는 [Jenkins의 Docker 설치 문서](https://www.jenkins.io/doc/book/installing/docker/)에서 설명하는 방식을 참고했다.

파일도 역할을 나눴다.

| 파일 | 역할 |
| --- | --- |
| `compose.jenkins.yaml` | Jenkins와 Docker-in-Docker 실행 |
| `jenkins/Dockerfile` | Docker CLI와 플러그인이 들어간 Jenkins 이미지 |
| `jenkins/casc.yaml` | Jenkins 기본 설정을 코드로 관리 |
| `compose.yaml` | 프론트엔드와 백엔드 앱 구성 |
| `Jenkinsfile` | 빌드·테스트·배포 순서 |
| `backend/tests/test_health.py` | 백엔드 API 테스트 |

기존에는 다른 실습 폴더의 Jenkins 설정을 사용했지만, 현재 프로젝트에서 관리할 수 있도록 이전했다. 계정과 빌드 기록을 유지하려고 기존 데이터 볼륨은 재사용했다.

따라서 저장소의 `git-lab_*` 볼륨 이름은 이전 환경에서 가져온 흔적이다. 다른 Mac에서 그대로 실행하려면 외부 볼륨을 별도로 준비하거나 자신의 환경에 맞게 볼륨 구성을 바꿔야 한다.

## 8080, 3000, 8000, 그리고 3001과 8001

기존 앱이 Mac의 3000과 8000 포트를 사용하고 있어서, Jenkins가 배포한 앱은 3001과 8001로 확인하도록 했다.

| Mac에서 접속하는 주소 | 대상 |
| --- | --- |
| `http://localhost:8080` | Jenkins |
| `http://localhost:3001` | Jenkins가 배포한 프론트엔드 |
| `http://localhost:8001/health` | Jenkins가 배포한 백엔드 상태 API |

앱 컨테이너 내부 포트는 여전히 3000과 8000이다. 바뀐 것은 Mac에서 접속하는 쪽의 포트다. `compose.jenkins.yaml`에서 Docker-in-Docker 컨테이너의 3000·8000을 Mac의 3001·8001로 연결한다.

주의할 점은 블로그 개발 서버도 3001을 사용한다는 것이다. 실습 앱과 블로그를 동시에 띄울 때는 둘 중 하나의 호스트 포트를 달리 잡아야 한다.

## GitHub 연결과 인증 문제

처음 저장소를 연결하는 과정에서는 `fatal: Authentication failed`가 나왔다. 실습 저장소는 공개 저장소로 바꿔서 익명 HTTPS 읽기를 할 수 있게 했다.

다만 공개 전환이 인증 오류의 일반적인 해결책은 아니다. 비공개 저장소를 유지해야 한다면 Jenkins Credentials에 토큰이나 SSH 키를 등록해 연결해야 한다. 공개 저장소에는 비밀번호나 토큰이 포함된 파일을 올리면 안 된다.

이번 구성의 관리자 계정 정보는 `.env.jenkins`에 두고 Git에서 제외했다. 글에도 실제 비밀번호나 토큰은 넣지 않았다.

Jenkins 작업은 **Pipeline script from SCM**으로 설정하고, GitHub의 `main` 브랜치에서 루트 `Jenkinsfile`을 읽도록 했다. 이렇게 하면 Jenkins 화면에만 빌드 절차를 저장하지 않고 코드와 함께 변경 이력을 관리할 수 있다.

## 변경 감지와 동시 실행 제한

```groovy
options {
    disableConcurrentBuilds()
    timeout(time: 15, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
    timestamps()
}

triggers {
    pollSCM('H/2 * * * *')
}
```

`pollSCM`은 주기적으로 저장소를 확인하고 변경이 있으면 빌드한다. 여기서는 약 2분 간격이다. `H`는 작업 이름 등을 바탕으로 실행 시점을 분산하기 위한 값이며, GitHub가 즉시 요청을 보내는 webhook 방식과는 다르다.

`disableConcurrentBuilds()`는 같은 작업을 동시에 실행하지 않도록 한다. 앞 빌드가 진행 중이면 다음 빌드는 기다린다. 다른 Jenkins 작업까지 함께 잠그는 설정은 아니다.

나머지는 에이전트 할당 후 전체 실행 시간을 15분으로 제한하고, 최근 빌드 기록 20개를 보관하며, 콘솔에 시간을 표시하는 설정이다. Jenkins 기록을 지운다고 Docker 이미지와 캐시까지 정리되지는 않는다.

새 Jenkinsfile의 트리거와 파라미터를 등록하려면 해당 파일로 한 번 실행해야 한다. 자세한 동작은 [Pipeline 문법 문서](https://www.jenkins.io/doc/book/pipeline/syntax/)에서 확인할 수 있다.

## stage 순서가 중요한 이유

실습하면서 가장 확실히 이해한 부분이다. 현재처럼 순차적으로 구성한 파이프라인은 `stage`를 위에서 아래로 실행한다.

```text
이미지 빌드 → 테스트 → 배포
               ↓ 실패
           이후 배포 생략
```

테스트를 배포 뒤에 두면 검사에 실패해도 앱은 이미 바뀐 상태다. 반대로 이미지 빌드보다 앞에서 테스트하면 이번 코드로 만든 이미지 대신 이전 이미지를 사용하거나, 필요한 이미지를 찾지 못할 수 있다.

그래서 백엔드 테스트는 **이미지 빌드 다음, 컨테이너 실행 이전**에 배치했다. `parallel`로 병렬 실행하거나 `when`으로 단계를 생략하는 구성도 가능하지만, 이번 핵심 경로는 순차 실행이다.

별도로 `FAIL_TEST` 체크박스와 `error()`를 이용한 실패 실습 단계도 만들었다. 정리 시점 파일에는 이 단계가 마지막에 남아 있다. 배포 전 중단을 실습하려면 `파일 확인` 다음으로 이동해야 하며, 일반 빌드에서는 체크를 해제한다.

## pytest로 배포 전에 API 검사하기

백엔드 의존성에 `pytest`, `httpx`를 추가하고 `/health`를 검사했다.

```python
from fastapi.testclient import TestClient

from app.main import app


def test_health():
    with TestClient(app) as client:
        response = client.get("/health")

    assert response.status_code == 200
    assert response.json() == {"status": "ok"}
```

`TestClient`는 실제 서버 포트를 열지 않고 애플리케이션에 요청한다. 이 검사는 API 동작을 확인하는 것이고, 배포한 서버에 외부에서 접속할 수 있는지까지 검사하는 것은 아니다.

Jenkins에서는 방금 빌드한 이미지로 임시 컨테이너를 실행한다.

```groovy
stage('백엔드 테스트') {
    steps {
        sh '''
            mkdir -p test-results
            rm -f test-results/backend.xml

            docker compose run --rm --no-deps \
                -v "$WORKSPACE/test-results:/test-results" \
                backend python -m pytest -q \
                --junitxml=/test-results/backend.xml
        '''
    }
    post {
        always {
            junit 'test-results/backend.xml'
        }
    }
}
```

`--rm`은 실행 후 임시 컨테이너를 삭제하고, `--no-deps`는 의존 서비스를 함께 시작하지 않게 한다. pytest가 실패하면 명령이 0이 아닌 종료 코드를 반환하므로 다음 배포 단계로 진행하지 않는다.

결과 파일은 JUnit XML 형식으로 저장한다. 단계 안의 `post { always { ... } }`에서 수집하므로 테스트에 실패해도 Jenkins의 Test Result에서 실패 내용을 볼 수 있다. 테스트 도구 자체가 실행되지 않아 XML이 만들어지지 않으면 결과 수집도 실패할 수 있다.

여기서는 Jenkins와 Docker-in-Docker가 `/var/jenkins_home`을 공유한다. 그래서 `$WORKSPACE` 경로를 Docker 엔진에서도 같은 위치로 볼 수 있다. 원격 엔진을 쓰는 다른 환경에서는 이 볼륨 명령을 그대로 복사하면 안 된다.

관련 문서는 [pytest 출력 설정](https://docs.pytest.org/en/stable/how-to/output.html)과 [Jenkins JUnit 단계](https://www.jenkins.io/doc/pipeline/steps/junit/)를 참고했다.

## 컨테이너 실행과 정상 응답은 다르다

앱을 시작할 때는 다음 명령을 사용했다.

```bash
docker compose up -d --wait --wait-timeout 120
docker compose ps
```

`-d`만으로는 앱이 정상 응답할 준비가 됐는지 알기 어렵다. 이번에는 프론트엔드와 백엔드에 healthcheck를 넣어서 `--wait`가 그 상태까지 기다리게 했다.

프론트엔드는 컨테이너 안의 Node.js로 HTTP 요청을 보낸다.

```yaml
healthcheck:
  test:
    - CMD
    - node
    - -e
    - "fetch('http://127.0.0.1:3000', {signal: AbortSignal.timeout(3000)}).then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
  interval: 10s
  timeout: 5s
  retries: 3
  start_period: 20s
```

백엔드는 Python으로 `http://localhost:8000/health`에 요청한다. 프론트엔드의 `depends_on`도 백엔드가 `service_healthy`가 된 후 시작하도록 설정했다.

배포 뒤에는 별도 단계에서 백엔드 응답을 읽고 JSON이 `{"status": "ok"}`인지 확인했다. 배포 전 pytest는 코드 동작을, 배포 후 검사는 실제 실행 중인 앱의 상태를 확인하는 셈이다.

다만 컨테이너 내부 healthcheck가 통과해도 Mac의 포트 연결까지 보장하지는 않는다. `localhost:3001`과 `localhost:8001/health` 접속은 별도로 확인한다.

## 테스트가 통과해도 승인 전에는 기다리기

```groovy
stage('배포 승인') {
    steps {
        timeout(time: 5, unit: 'MINUTES') {
            input(
                message: '테스트를 통과했습니다. 앱을 배포할까요?',
                ok: '배포 진행'
            )
        }
    }
}
```

이 단계를 테스트와 컨테이너 실행 사이에 넣었다. GitHub 변경으로 빌드와 테스트는 시작되지만, 배포는 사람이 승인해야 진행된다.

5분 동안 승인하지 않거나 사용자가 중단하면 보통 `ABORTED`로 끝난다. 전체 파이프라인의 15분 제한도 함께 적용되므로 승인 대기 시간이 항상 5분 보장되는 것은 아니다. [Input 단계 문서](https://www.jenkins.io/doc/pipeline/steps/pipeline-input-step/)에서 동작을 확인할 수 있다.

## 실패했을 때 남겨야 할 것

전체 파이프라인의 `post`에는 성공·실패·중단 처리를 넣었다. 실패 시에는 다음 명령으로 상태와 최근 로그를 출력한다.

```groovy
failure {
    sh(script: 'docker compose ps -a', returnStatus: true)
    sh(
        script: 'docker compose logs --no-color --tail=100',
        returnStatus: true
    )
}
```

진단 명령에도 `returnStatus: true`를 사용해서 명령의 실패가 곧바로 예외가 되지 않게 했다. 원래 빌드 실패를 성공으로 바꾸는 설정은 아니다.

실패 처리 실습은 두 가지로 나눴다. `error()`는 파이프라인의 실패 후처리를 확인하고, 테스트 기대값을 잠시 `{"status": "wrong"}`으로 바꾸는 방법은 실제 테스트 실패가 배포를 막는지 확인한다. 현재 테스트 기대값은 정상값으로 복구돼 있다.

배포 전에 실패했다면 실행 중인 기존 앱은 이번 파이프라인에 의해 교체되지 않는다. 하지만 컨테이너 교체나 배포 후 검사에서 실패하면 앱 상태가 이미 달라졌을 수 있다. 현재 구성에는 자동 롤백이 없다.

## 어떤 코드를 배포했는지 기록하기

이미지에 빌드 번호를 붙이기 위해 Jenkinsfile에 환경 변수를 추가했다.

```groovy
environment {
    IMAGE_TAG = "${BUILD_NUMBER}"
}
```

Compose에서는 이 값을 이미지 태그로 사용한다.

```yaml
services:
  backend:
    image: "docker_practice-backend:${IMAGE_TAG:-local}"
    build: ./backend

  frontend:
    image: "docker_practice-frontend:${IMAGE_TAG:-local}"
    build: ./frontend
```

위 코드는 이미지 관련 부분만 발췌한 것이다. 실제 파일의 포트, 의존성, healthcheck 설정은 유지한다.

빌드가 `#25`라면 두 이미지에 `:25`가 붙는다. Jenkins 밖에서 변수를 지정하지 않으면 `local`을 사용한다. [Compose 변수 치환 문서](https://docs.docker.com/reference/compose-file/interpolation/)의 기본값 문법이다.

빌드·테스트·배포가 같은 환경 변수를 사용하므로, 이번에 만든 이미지를 검사하고 실행할 수 있다. 태그는 사람이 덮어쓸 수 있는 이름이므로 이미지 자체의 불변 식별자와 같지는 않다.

성공 후에는 아래 정보를 `deployment-info/deployment.txt`에 남기고 `archiveArtifacts`로 해당 빌드에 보관했다.

```text
BUILD_NUMBER=빌드 번호
IMAGE_TAG=이번 빌드의 이미지 태그
BUILD_URL=해당 Jenkins 빌드 주소
GIT_COMMIT=체크아웃한 전체 커밋 해시
VERIFIED_AT_UTC=상태 확인 후 기록한 UTC 시간
```

Jenkins의 Artifacts에서 다운로드할 수 있다. [아티팩트 보관 문서](https://www.jenkins.io/doc/pipeline/steps/core/#archiveartifacts-archive-the-artifacts)에 설명된 기능이다. 생성 파일인 `test-results/`, `deployment-info/`는 Git에서 제외했다.

여기까지는 Jenkins가 사용하는 Docker 엔진에 이미지를 남기는 구성이다. Docker Hub 같은 레지스트리에 업로드하지는 않는다.

## 롤백 실습 예제: 이전 이미지를 다시 실행하기

롤백은 이전 성공 빌드의 이미지로 컨테이너를 다시 실행하는 방식으로 실습 절차를 정리했다. 아래 번호는 설명용이며, 이 글에서 롤백 성공 결과를 확인했다고 주장하는 것은 아니다.

일반 빌드나 승인 대기 중인 배포가 없는 상태에서 Jenkins 컨테이너에 들어간다.

```bash
docker exec -it jenkins bash
cd /var/jenkins_home/workspace/hello-pipeline

docker image ls docker_practice-backend
docker image ls docker_practice-frontend
```

두 이미지가 모두 남아 있고 과거 테스트와 배포가 성공했던 번호를 고른다. 예를 들어 `25`라면 다음처럼 대상 이미지가 있는지 먼저 확인한다.

```bash
export IMAGE_TAG=25
docker image inspect "docker_practice-backend:$IMAGE_TAG" > /dev/null
docker image inspect "docker_practice-frontend:$IMAGE_TAG" > /dev/null
```

둘 중 하나라도 없으면 진행하지 않는다. 둘 다 확인되면 기존 배포 프로젝트를 지정해 교체한다.

```bash
docker compose -p hello-pipeline up \
    -d --no-build --pull never --wait --wait-timeout 120
docker compose -p hello-pipeline ps
```

`--no-build`는 새 이미지 생성을 막고, `--pull never`는 엔진에 남아 있는 이미지만 사용하게 한다. 관련 옵션은 [Compose up 문서](https://docs.docker.com/reference/cli/docker/compose/up/)에서 확인할 수 있다.

이 방식은 현재 작업 폴더의 Compose 설정으로 예전 이미지를 실행한다. Git 코드, 환경 설정, 데이터베이스나 파일 데이터까지 과거로 돌아가는 것은 아니다. 컨테이너를 교체하므로 무중단 배포도 아니다. 실행 후 이미지 태그와 두 서비스의 `healthy`, 브라우저 접속을 확인해야 한다.

이어서 Jenkins에 별도 `app-rollback` 작업을 만들고, `TARGET_TAG` 입력 → 숫자 검증 → 두 이미지 존재 확인 → 설정 checkout → 롤백 승인 → 위 명령 실행 순서로 구성하는 방법도 다뤘다. 별도 작업의 실제 생성·실행 결과는 이 글의 확인 범위에 포함하지 않았다.

롤백 작업을 만들 때는 새 작업 폴더 이름으로 별도 앱이 생성되지 않도록 `-p hello-pipeline`을 지정해야 한다. 또 `disableConcurrentBuilds()`는 일반 배포 작업과 롤백 작업 사이의 동시 실행을 막지 못한다. 현재 실습 절차는 두 작업을 동시에 실행하지 않는 것을 전제로 한다.

## 실습하면서 남은 것

처음에는 Jenkins가 명령어를 대신 실행해주는 도구처럼 보였다. 지금은 어떤 검사가 통과해야 다음 단계로 넘어가는지, 실패했을 때 어디서 멈췄는지, 배포한 코드가 무엇인지 기록하는 역할까지 보인다.

특히 테스트를 어느 위치에 두느냐에 따라 배포를 막을 수 있는지가 달라진다는 점이 가장 기억에 남았다. 테스트 파일을 만드는 것만큼 실행 순서도 중요했다.

현재 구성은 Mac에서 흐름을 이해하기 위한 실습이다. Docker-in-Docker의 privileged 실행, 단일 Jenkins 실행 환경, 로컬 이미지 보관을 그대로 운영 표준으로 삼기보다는, 다음에는 레지스트리 보관과 배포·롤백 간 동시 실행 제어를 더 살펴보려고 한다.
